# 麻雀ラボ：開発者向けセキュリティ演習

mainブランチの麻雀ゲーム本体を使う、架空データだけの演習版です。猫と牌の画面、30秒タイマー、出題・採点、清一色への切替、終了後の振り返りは元の実装をそのまま再利用しています。通常版のファイル、接続設定、DBスキーマは変更していません。

## まずローカルで動かす

Node.js 24以上で、リポジトリのルートから実行します。依存のインストールやビルドは不要です。

```sh
node workshop/server.js
```

`http://127.0.0.1:4173` を開き、ターミナルに表示されるペア1またはペア2の参加コードで入室してください。`localhost` ではなく、表示されたURLを使用します。参加コードは `neko-`・`tile-` などの語とランダム5文字を組み合わせた10文字です。ローカル版は起動ごとに生成、Supabase版はSecretsへ設定したコードを継続利用します。別ペアの確認には別のブラウザプロファイルを使います。サーバーはループバックアドレスだけで待ち受けます。

- SQLiteの実SQLを使います。SQLiを文字列比較で模擬しているものではありません。
- ペアごとに別のメモリ内DBを作り、検索接続は読み取り専用です。
- 名前と進捗はサーバーメモリに保存され、ページ再読み込み後も残ります。プロセス再起動で全領域が消えます。
- 「このモードをリセット」は自分の現在のモードだけを初期化します。
- 弱点版・修正版の名前と進捗は独立しています。比較時は同じ入力をもう一度保存してください。
- 演習はHTTP APIが必要です。通常版の `index.html` の `file://` 動作はそのままですが、演習版は `file://` では動きません。

## 元ゲームとの接続

- 入室すると元の「麻雀 待ち当て」開始画面が開きます。「はじめる」で30秒ゲームを遊べます。
- 終了時の実際の得点・正解数・回答数・最高連続を演習APIに保存し、マイページの統計と最近のプレイ、上位10件ランキングへ反映します。
- 元のマイページに非公開メモ、表示名の安全なプレビュー、登録者検索を追加しています。開始画面から開けるので麻雀を解かずに演習できます。
- ランキングの保存名の描画だけはsandbox付きiframeに隔離しています。終了画面のランキングと、開始画面から開くランキングは同じデータ・描画領域を使います。
- ゲーム中はモード変更・リセット・退室を無効化します。課題を開いてもゲームの時計は止まりません。
- `main.js`、`mahjong-logic.js`、`tile-art.js`、`ranking.js`、`style.css` はルートの元ファイルと同一です。`index.html` は元HTMLに演習用の差分を加えています。通常版の `online.js` と `account.js` を読み込まず、`app.js` の演習用アダプターで接続します。
- 元ゲームを更新した際は `node workshop/sync-game.js` で同期できます。生成済みファイルを含むため、通常の起動・配信にビルド工程は不要です。
- 得点は元ゲームと同様にクライアントで計算し、APIは範囲を検証します。得点改ざん耐性を追加したものではなく、今回の課題対象外です。

## 3問の内容

問題文・3段階のヒント・原因と修正は画面内にあります。表示は易しいと想定する順にSQLi→XSS→IDORです。検索欄だけで試せる課題から、保存・描画の経路を追う課題、通信を変更・再送する課題へ進みます。難易度は事前試行で調整します。

| 問題 | 到達目標 | 意図的な弱点 | 修正版 |
| --- | --- | --- | --- |
| 非掲載の登録名 | SQLで非掲載の架空登録者を取得して証拠コードを提出 | 検索語をSQLに連結 | パラメータ化 |
| ランキングを書き換える | 保存した名前を経由してJSを実行し、DOMバナーを追加 | 名前をランキングでinnerHTMLに渡す | textContentで文字として表示 |
| 他人のマイページ | ライバルの非公開メモの合言葉を提出 | 同一領域内のプロフィール所有者チェック欠落 | 本人の101以外を404にする |

ランキングのニックネームと非掲載の登録名は別データです。「すでに公開されている名前を取得して成功」という問題にはしていません。

1. 検索欄へ `' OR 1=1 -- `（末尾に空白）を入力。非掲載名とレスポンスの `NAME-...` を確認して提出。
2. 名前を `<img src=x onerror="celebrate()">` にして保存。プレビューは文字のままであることを確認し、ランキングを開く。sandbox内で画像読み込みが拒否されるとonerrorが実行され、教材関数がDOMを追加し成功通知を送る。

修正版では、IDORは404、SQLiは非掲載名なし、XSSは入力文字がそのまま表示されます。正常なプロフィール取得・「公開」の検索・普通の名前表示は維持します。

### Supabase側の分離

- ペアごとに専用スキーマ、readerログイン、writerログインを作ります。ロールは管理権限・他ロールのメンバーシップ・BYPASSRLSを持ちません。
- readerは自分の `directory` のSELECTだけ、writerは自分の `state` のSELECT/INSERT/UPDATEだけを持ちます。所有者はいずれの接続ロールとも異なります。
- SQLiはreader接続の読み取り専用トランザクションだけで実行します。writerはパラメータ化した固定クエリだけです。
- 検索語以外のスキーマ名・接続資格情報は、検証済みセッションに対応するサーバー設定から決めます。bodyの領域指定は使用しません。
- ペア別の接続プールを使います。管理者ログインから `SET ROLE` する構成ではありません。
- SQLiクエリにも固定のバインド引数を置き、複文を受け付けないextended query経路を使います。これは意図したWHERE条件のSQLiを防ぐものではありません。
- 進捗・秘密メモ・XSSチケットはreaderが読めない `state` に保存します。DB行ロックで同じモードの更新とリセットを直列化します。
- ペアの状態を別テーブル権限で守る設計であり、任意SQLから変更可能な `lab_id` セッション変数やWHERE句に境界を依存させません。
- DBシステムカタログの一部やDB資源自体は共有されます。これは物理分離ではなく、負荷攻撃を防ぎきる環境ではありません。強い分離が必要ならペア別プロジェクトを使用します。
- 教材スキーマをData APIの公開スキーマに追加しません。既存の権限追加・SECURITY DEFINER関数を持ち込まず、新規の教材プロジェクトで検証します。

### クラウドの転送形式と実通信テスト

Supabaseの入口にあるCloudflareが生の教材用SQLi文字列をGET・POSTともに403で遮断したため、ブラウザはPOST本文を `{encoding:"base64-json",data:"…"}` として転送します。APIでUTF-8のJSONへ復号してから処理します。これは暗号化・認可・SQLi対策ではありません。修正版のパラメータ化とDB権限が実際の防御です。「演習課題」に復号方法を表示しています。IDORの取得URLは通常のGETのままです。

PostgreSQLのJSONBには `sql.json()` でオブジェクトを保存します。事前に `JSON.stringify()` した文字列をJSONBへ渡すと二重エンコードになることを実DBで確認して修正しました。

```sh
node workshop/check-remote.js --connection-only
```

検証用参加者を新規登録して接続を確認します。`--connection-only` を省略すると課題・参加者分離を検証し、作成した検証ユーザーだけをリセットします。既存参加者の状態は変更しません。検証用の登録データはDBに残ります。資格情報は出力しません。

### 静的配信時のヘッダー

ローカルサーバーは設定済みです。Supabaseを使って別ホスティングに置く場合、フロントに次を設定し、connect-srcの接続先だけ教材APIへ変更してください。

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-src 'self'; connect-src 'self' https://<教材project-ref>.supabase.co; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
Cache-Control: no-store
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

`ranking-frame.html` だけは次のCSPにします（HTML内にも同等のmeta CSPがあります）。親ページの厳しいscript-srcをこのファイルへ重複設定すると演習用イベント属性も止まります。

```text
Content-Security-Policy: default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'unsafe-inline'; img-src 'none'; connect-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors 'self'
```

iframeのsandboxは `allow-scripts` のみです。`allow-same-origin`・フォーム・ポップアップ・トップナビゲーション許可を追加しません。参加セッションは親画面のsessionStorageに置き、iframeには渡しません。名前をHTMLとして描画する箇所はiframe内の一箇所だけです。

## 40分の進行例

導入・正常操作7分、マイページ10分、SQLi10分、解説と修正比較10分、振り返り3分。XSSは早期終了者向けの追加問題にすると当初の40分枠に収まります。3問全員必須にする場合は、各問の時間を短縮するより開催枠を延長する方が原因と修正の説明時間を確保できます。


## 参加者名での登録

入口で参加者名（1〜40文字のニックネーム）と参加コードを入力します。同じコード・同じ名前でも、登録ごとに新しい参加者IDを発行します。名前は本人確認には使いません。

Supabase版はスキーマ内の `state` に `(participant_id, mode)` をキーとして、登録名・表示名・記録・進捗をJSONで保存します。参加者IDはサーバーが発行し、署名付きセッションに含めます。API本文で他人のIDを指定してもアクセス主体は変わりません。検索用readerは状態表を読めず、SQLiで他の実参加者の名前は取得できません。検索対象は本人と架空ユーザーです。ローカル版はメモリ保存で、サーバー停止時に消えます。

再読み込みは同じタブのセッションを継続します。退室・タブを閉じる・8時間の有効期限切れ後にフォームから登録すると新しいユーザーになります。名前とコードによる過去ユーザーへの再ログイン機能はありません。リセットは自分の選択中モードだけを初期化し、登録名は保持します。

既存DBには `supabase/migrations/202610180002_participants.sql` を適用します。旧データは `participant_id = 'legacy'` として保持され、既存の旧セッションから引き続き参照できます。新規登録者とは分離されます。専用プロジェクトには適用済みです。


### 固有ユーザーレコード

`202610180003_users.sql` 適用後、初回登録では各スキーマの `users` に固有UUID・参加者ID・登録名・作成日時を保存します。`state.participant_id` は外部キーでユーザーに紐づきます。登録と両モードの状態作成は同一トランザクションです。既存参加者もレコードを作成して移行し、既存セッション・進捗を保持します。

`/status` の `me` が本人の固有IDです。フロントは `/profiles/{me}` を取得し、プレイ記録にも同じIDを使います。`202610180004_profile_numbers.sql` により、プロフィールIDは各スキーマで101から始まる連番（users.profile_id）になりました。内部のusers.idと署名セッションの参加者IDはUUIDのままです。ライバルのプロフィールIDは本人+1です。例えば本人101なら102、本人108なら109を使います。同じ番号が別の実参加者に割り当てられていても、APIは常に現在の演習領域の架空ライバルだけを返します。修正版は本人以外を拒否します。採番はDBのIDENTITYを使うため、取り消した登録などで欠番が生じる場合があります。users表は検索用readerから読み取れません。登録名と、モード別に変更できる表示名は区別しています。
